## CUDA on eight NVIDIA GPUs

The series starts with 13 optimizations on L4. Seven more PRs select which paths to run on each additional GPU for the same Qwen3.6-35B-A3B INT4 checkpoint. Each PR has a record of its measurements. [Start with PR #2979](https://github.com/JustVugg/colibri/pull/2979) · [Integration batch #3064](https://github.com/JustVugg/colibri/pull/3064)

I compared the full stack (`da49a161`) with `dev` (`05245ef4`) on the same physical card for each pair. **All 384 comparisons matched `dev` bit for bit** across 16 workloads, three runs and eight GPUs. Each comparison covered the full FP32 logits after reading the prompt and at every generation step. On the RTX PRO 4000, a single cold 64-token run checked 129 vectors × 248,320 logits (32,033,280 FP32 values) with zero differences. All 1,024 vectors in the separate perplexity check also matched. [RTX PRO 4000 correctness record](https://github.com/CoTi1938/colibri/blob/7b46ef57d3363c9ba9cdbf85dc93022971e77028/docs/experiments/qwen36-cuda-16-rtx-pro-4000-2026-11-22/correctness.txt)

## The first Metal graph

I built colibri’s Metal inference graph for Qwen3.6 so the forward pass could run on Apple Silicon while the model’s routed experts stayed on disk. A bounded cache brings the experts into memory as the model needs them. That let me run the 35B model on a fanless MacBook Air M1 with 8 GB of unified memory. The graph, its kernels and its expert cache are all in `main`. [Graph PR](https://github.com/JustVugg/colibri/pull/2298) · [Metal implementation guide](https://github.com/JustVugg/colibri/blob/main/docs/qwen36-metal.md)

On the 512-token prompt, the first decode step took **283 ms on Metal** and **1,032 ms on the CPU** (medians of four runs). In a separate test, both engines processed the same 1,024 continuation tokens one at a time. Metal ran at **8.79 tokens/s**, the CPU at **1.89**. Their mean negative log-likelihoods were 2.945 and 2.948 respectively. [Four-run timings](https://github.com/JustVugg/colibri/blob/e479104ae01bdc40ce81e675299b1d230891b321/docs/experiments/qwen36-metal-graph-2026-10-05/summary.txt) · [Same-text comparison](https://github.com/JustVugg/colibri/blob/e479104ae01bdc40ce81e675299b1d230891b321/docs/experiments/qwen36-metal-graph-2026-10-05/quality.txt)

## More work in upstream `main`

- **First token on a 74 GiB model.** On an L4, Qwen3.8 filled VRAM so tightly that the CPU had to take over. Leaving room for the GPU’s working buffers cut the wait for the first token of a 1,628-token prompt from **450.3 to 45.6 seconds**. On a short prose run, holding fewer experts on the card cost 2.1% in generation speed. [PR #2413](https://github.com/JustVugg/colibri/pull/2413) · [L4 benchmark](https://github.com/JustVugg/colibri/blob/e479104ae01bdc40ce81e675299b1d230891b321/docs/experiments/qwen38-auto-tier-number-2026-10-26/long-prompt.txt#L568-L587)
- **Vulkan startup on the L4.** Qwen3.6 was still loading its experts after 15 minutes in all four attempts. Detecting how much VRAM the driver could map let the engine select staged uploads automatically. The experts were ready in **21 seconds**. [PR #2422](https://github.com/JustVugg/colibri/pull/2422) · [Startup log](https://github.com/JustVugg/colibri/blob/e479104ae01bdc40ce81e675299b1d230891b321/docs/experiments/vulkan-staged-small-window-2026-10-27/l4.txt#L38-L52)
- **A 35B GGUF on an 8 GB Mac.** The Metal graph gained support for reading quantized weights directly from a GGUF file. On the M1 Air, faster kernels took a 512-token prose prompt from **12.8 to 69.1 tokens/s** and generation from **5.22 to 7.48 tokens/s**, both against the first GGUF implementation. [GGUF support #2306](https://github.com/JustVugg/colibri/pull/2306) · [Kernel measurements #2307](https://github.com/JustVugg/colibri/pull/2307) · [GGUF benchmarks](https://github.com/JustVugg/colibri/blob/e479104ae01bdc40ce81e675299b1d230891b321/docs/experiments/qwen36-gguf-metal-2026-10-19/README.md#the-kernels-the-change-before-against-this-one-on-the-gguf)
- **One GPU transfer per output on the RTX PRO 4000.** Qwen3.6 wrote 248,320 separate scores across the bus at each decode step. Collecting them on the card and copying them together raised generation from **74.7 to 145.1 tokens/s** with the same logits. The extra copy cost 0.6–0.7% on the L4. [PR #2421](https://github.com/JustVugg/colibri/pull/2421) · [Decode runs](https://github.com/JustVugg/colibri/blob/e479104ae01bdc40ce81e675299b1d230891b321/docs/experiments/qwen36-cuda-lmhead-device-2026-10-27/pro4000-normal.txt#L604-L654)
- **Sampling a token on the M1.** The chat sampler used to sort all 248,320 probabilities at every draw. Sorting just the candidates brought the draw from **23.6 to 1.1 ms** (42.4 → 906.3 draws/s) on three Qwen3.6 replies at the gateway defaults. Every tested draw at those settings picked the same token as before. [PR #2012](https://github.com/JustVugg/colibri/pull/2012) · [Sampling benchmark](https://github.com/JustVugg/colibri/blob/e479104ae01bdc40ce81e675299b1d230891b321/docs/experiments/qwen36-serve-sampler-2026-10-08/manifest.json)
- **An eight-turn agent session on the T4.** Keeping the RAM copies in sync as experts moved on and off the GPU cut a replay with tool calls from **71.6 to 43.1 seconds**. A separate five-turn chat with short follow-up prompts took 37.3 seconds on both builds. [PR #2416](https://github.com/JustVugg/colibri/pull/2416) · [Session timings](https://github.com/JustVugg/colibri/blob/e479104ae01bdc40ce81e675299b1d230891b321/docs/experiments/qwen36-cuda-host-pool-follow-2026-10-26/sessions.txt#L117-L173)
- **Container cgroup memory limits on Linux.** `/proc/meminfo` reports the host’s RAM rather than a container’s quota (on a rented RTX PRO 4000 container, `MemAvailable` showed 195.7 GiB against a 120.7 GiB cgroup limit). Bounding the C memory reader by cgroup v2/v1 limits and counting reclaimable `active_file` cache kept engines and the planner from over-allocating or under-planning after `mmap` reads (24.18 vs 14.88 GB reported in a 24.22 GB container, 22.18 GB allocated with zero OOM kills). [C reader #2396](https://github.com/JustVugg/colibri/pull/2396) · [Planner #2397](https://github.com/JustVugg/colibri/pull/2397)
